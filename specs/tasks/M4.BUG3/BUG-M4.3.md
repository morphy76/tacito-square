## Problem Statement

The application currently integrates two overlapping observability frameworks: the native Prometheus client library (`github.com/prometheus/client_golang`) for metrics collection, and the OpenTelemetry client library (`go.opentelemetry.io/otel`) for distributed tracing. 

This architectural overlap deviates from modern, unified observability standards. OpenTelemetry provides a unified API and SDK for both tracing and metrics. Using both libraries increases codebase complexity, leads to fragmented instrumentation, makes context correlation between metrics and traces difficult, and introduces redundant dependency footprints.

## Impact

1. **Fragmented Telemetry Lifecycle**: The metrics and tracing lifecycles are initialized and managed separately, complicating bootstrapping and graceful shutdown logic.
2. **Context Correlation Gaps**: Correlating traces and metrics (e.g., trace exemplars) is highly complex or unsupported when using disconnected telemetry clients.
3. **Dependency Bloat**: Maintaining direct dependencies on both Prometheus and OpenTelemetry client libraries increases binary size and maintenance overhead.

## Expected Behaviour

1. **Unified Telemetry API**: Direct usage of `github.com/prometheus/client_golang` for creating, registering, and recording application metrics MUST be removed and replaced with the OpenTelemetry Go metrics API (`go.opentelemetry.io/otel/metric`).
2. **Prometheus Compatibility**: The GET `/metrics` endpoint MUST continue to serve standard Prometheus exposition format telemetry, achieved by mounting the official OpenTelemetry Prometheus exporter (`go.opentelemetry.io/otel/exporters/prometheus`).
3. **Trace-Metric Correlation**: Metrics recorded under active HTTP requests should automatically correlate with OpenTelemetry tracing contexts when available.

## Acceptance Criteria

1. Direct imports of `github.com/prometheus/client_golang/prometheus` in metrics recording and registry flows are removed.
2. All application metrics (HTTP durations, requests, active threads, agent status, etc.) are successfully registered and recorded using OTel instruments.
3. The GET `/metrics` endpoint returns valid Prometheus metrics exposition format generated by the OTel Prometheus exporter.
4. Existing test suites are updated to verify metric generation using OTel and remain fully green.
