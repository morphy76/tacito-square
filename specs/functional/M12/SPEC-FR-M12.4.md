## Context

Currently, all agents in a community must be manually configured from scratch with custom brain configurations, memory settings, prompts, and skills. To simplify community creation and standard operations, the system requires a set of pre-defined, built-in agent templates. 

These include specialized routing/bridging components (like the Community Gateway), built-in utility agents (like the Response Polisher and Echo Agent), and standard cognitive agents.

## Specification

### 1. Built-in Agent Catalog

The system MUST support the following built-in agent templates:

#### A. Community Gateway (`community-gateway`)
* **Role**: A stateless bridging and routing agent. It DOES NOT possess a cognitive reasoning engine, memory (STM/LTM), skills, or configurable prompt templates.
* **Functionality**: Bridges public-facing end-user endpoint events from NATS to the community's entry agent.
* **Routing Logic**:
  * In a `single-agent` (standalone) topology: Routes inbound user events directly to the sole standalone agent's NATS subject.
  * In a `hub-spoke` topology: Routes inbound user events to the Hub agent coordinator's NATS subject (`ts.community.{id}.agent.hub`).
  * In a `sequential` topology (future): Routes inbound user events to the first agent in the sequence, and listens to the last agent in the sequence to bridge the final response back.
* **Deployment Scope**: Deployed as a multi-tenant unit or a dedicated single-tenant instance depending on deployment configuration.

#### B. Response Polisher (`response-polisher`)
* **Role**: A specialized utility agent/skill template.
* **Functionality**: Decoupled from the Hub coordinator. It takes a raw, intermediate response generated by another agent and applies polishing/formatting rules before returning the output.

#### C. Hub Agent Coordinator (`hub-coordinator`)
* **Role**: A built-in orchestrator template.
* **Functionality**: Coordinates and manages inter-agent messaging and task execution for `hub-spoke` communities using the asynchronous state machine.

#### D. Standard Cognitive Agent (`standard-cognitive`)
* **Role**: A general-purpose reasoning agent.
* **Functionality**: Uses a default pre-configured LLM brain, standard memory configurations, and default prompt templates to act as a fallback reasoning actor.

#### E. Echo / Diagnostic Agent (`echo-diagnostic`)
* **Role**: A lightweight diagnostic agent template.
* **Functionality**: Simplifies integration testing, latency profiling, and network diagnostics. It immediately echoes back incoming message payloads along with execution metadata (agent name, community, timestamp) without calling an LLM.

#### F. STM Summarizer (`stm-summarizer`)
* **Role**: A built-in utility agent template for memory optimization.
* **Functionality**: Reduces the token footprint of an agent's private per-agent Short-Term Memory (STM) for a given thread to optimize future interactions. It is triggered prior to or during agent execution.
* **Logic**:
  * **Evaluation**: The summarizer first evaluates the current thread history size (message count or cumulative token usage) against configured thresholds.
  * **Smart No-op Decision**: If the footprint is below the threshold, or if no significant compression can be achieved without losing critical recent context, the summarizer completes as a `noop` (no-operation) without modifying the memory.
  * **Summarization**: If thresholds are exceeded, it reads the older turns in the per-agent STM, generates a consolidated summary utilizing a lightweight LLM brain (preserving key decisions, user intent, and state), and replaces the summarized turns in the Redis keyspace with a single summary message block. Subsequent reasoning cycles for this agent on this thread will use this consolidated state to minimize prompt tokens.

### 2. Provisioning & Lifecycle (Template Cloning & Decoupled Assignment)

1. **Templates vs. Instances Distinction**:
   * **Agent Template**: A read-only predefined blueprint (statically defined globally or seeded in the system). An agent template cannot be directly assigned to a community and has `community_id = nil`.
   * **Agent Instance (Unassigned)**: A mutable copy of an agent template or custom agent configuration. It is scoped to a specific tenant but is not yet assigned to any community (`community_id = nil`).
   * **Agent Instance (Assigned)**: A concrete deployable entity associated with exactly one community (`community_id = active_community_id`).
2. **Cloning Flow**:
   * Any agent configuration (template or custom agent) that is **not already assigned** to a community (`community_id = nil`) CAN be cloned.
   * To clone an agent, the Keeper exposes a clone endpoint:
     `POST /api/v1/agents/:agent_id/clone`
   * The cloning operation does NOT require or accept a `community_id`.
   * On cloning, the Keeper:
     1. Deep-copies the source configuration (role, short-term memory config, long-term memory config, skills, prompt templates, and MCP clients).
     2. Generates a new unique `ID` (UUID) for the cloned agent.
     3. Scopes the clone by setting `tenant_id` to the active tenant.
     4. Initializes `community_id` to `nil` (the cloned agent remains unassigned).
     5. **Brain Provisioning**: For clones that require an LLM Brain, the Keeper resolves the tenant's default LLM provider binding and injects its ID into `brain.llm_binding_id`.
3. **Decoupled Assignment**:
   * Once cloned, the tenant can optionally customize the new agent instance (e.g. change its name, attach skills).
   * The agent is assigned to a community using the standard assignment API:
     `POST /api/v1/communities/:community_id/agents/:agent_id`
   * Assigning the agent sets the `community_id` and transitions its status to `assigned`, triggering deployment by the Kubernetes Operator.

---

### 3. Multitenancy Boundaries

* The `community-gateway` is designed to be a **shared multi-tenant unit** or a **dedicated single-tenant unit** depending on deployment topology.
* As a multi-tenant candidate, it MUST:
  * Route messages dynamically based on tenant and community identifiers extracted from NATS headers (`X-Tacito-Tenant`, `X-Tacito-Community`).
  * Enforce strict tenant isolation boundaries at the network and routing layers.

## Acceptance Criteria

1. Built-in agent templates are registered in the database as read-only blueprints.
2. The Keeper REST API exposes a clone endpoint `POST /api/v1/agents/:agent_id/clone` that duplicates any unassigned agent or template.
3. The cloning endpoint does not accept a `community_id` and creates the clone as an unassigned agent (`community_id = nil`).
4. On cloning templates requiring an LLM Brain, the Keeper automatically resolves the active tenant's default LLM binding and assigns its ID to the cloned agent.
5. The cloned agent can be modified and subsequently assigned to a community using `POST /api/v1/communities/:community_id/agents/:agent_id`.
6. The Kubernetes Operator correctly reconciles and deploys the cloned agent instances (and the community gateway) when they are assigned to a community.
7. The `community-gateway` successfully routes messages based on the community's topology.
8. The `echo-diagnostic` agent responds to messages by returning a structured echo payload without contacting external LLM APIs.
9. The `stm-summarizer` agent successfully reads the per-agent STM for a thread, evaluates token/message thresholds to decide if a noop is appropriate, and, if not, compresses the memory footprint by replacing older turns with a consolidated summary block in Redis.

## Test Plan

* **Unit Tests**:
  * Verify that seeding creates read-only agent templates.
  * Verify that the clone endpoint accepts any unassigned agent and duplicates its configuration.
  * Verify that the clone endpoint rejects cloning if the source agent is already assigned to a community.
  * Verify that the cloned agent has `community_id = nil` and a unique ID.
  * Verify that cloning a brain-enabled template dynamically resolves and assigns the tenant's default LLM binding ID.
  * Verify `community-gateway` routing logic correctly selects subjects based on standalone vs. hub-spoke topology configurations.
  * Verify that `stm-summarizer` correctly compresses a list of messages into a single summary block plus the remaining active context window when thresholds are exceeded.
  * Verify that `stm-summarizer` executes a noop when memory footprint is below configured thresholds.
* **Integration Tests**:
  * Verify end-to-end messaging where a message sent to `community-gateway` routes to a standalone agent and back.
  * Verify `echo-diagnostic` returns expected message and timestamp metadata.
  * Verify that invoking `stm-summarizer` on a per-agent thread STM key reduces the stored message count when thresholds are exceeded, while maintaining thread continuity in subsequent cognitive turns.
