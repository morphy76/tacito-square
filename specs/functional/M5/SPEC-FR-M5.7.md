## Context

In many deployments, and in particular in local or test environments, it is useful to run a specific Agent instance as a standalone, statically configured workload in Kubernetes, completely independent of the dynamic Keeper lifecycle APIs and the Kubernetes Operator controller. This is highly useful for static pipelines, debugging, and simple single-agent setups.

This specification introduces a new standalone Helm Chart (`tools/helm/tacito-agent`) that packages the TacitoAgent container. Since the agent does not contact the Keeper to retrieve its configuration in standalone mode, all required dynamic properties (such as LLM brain details, custom system prompts, and memory dimensions) are provided directly in the Helm values and mounted as an internal Kubernetes ConfigMap which is loaded as environment variables into the pod. The agent continues to utilize and connect to external, shared infrastructure dependencies (like NATS, Redis, and Qdrant).

As the only external interface for the agent is the NATS message bus, the helm needs to provide a client component to interact with the agent (e.g. a web interface or a CLI tool or a CURL endpoint, the easiest one). This client component will use the NATS API to send messages to the agent and receive messages from the agent. The optimal approach for the client component is to leverage existing third party NATS clients to publish messages to the agent, if third party tools are not available stop processing this specification.

## Specification

1. **Helm Chart Creation**:
   - A new Helm Chart MUST be created under `tools/helm/tacito-agent`.
   - The chart MUST follow standard Helm 3 structure (containing `Chart.yaml`, `values.yaml`, and a `templates/` directory).

2. **Structured Configuration Values**:
   - The chart's `values.yaml` MUST support structured configuration parameters covering:
     - **Agent Metadata**: `agent.id` (UUID), `agent.name` (string), `agent.tenantId` (string), `agent.communityId` (UUID).
     - **LLM Brain Configuration**: `agent.llm.model` (string), `agent.llm.endpoint` (string), `agent.llm.temperature` (float), `agent.llm.maxTokens` (int), `agent.llm.credentialsSecret` (string or secret reference).
     - **System Prompt**: `agent.systemPrompt` (string, multi-line).
     - **Short-Term Memory (Redis)**: `redis.url` (string), `redis.keyNamespace` (string), `redis.ttlSeconds` (int).
     - **Long-Term Memory (Qdrant)**: `qdrant.url` (string), `qdrant.collectionName` (string), `qdrant.vectorDimension` (int).
     - **Event Bus (NATS)**: `nats.url` (string).
     - **Object Storage (S3/MinIO)**: `s3.url` (string), `s3.bucket` (string).

3. **Kubernetes ConfigMap Generation**:
   - The Helm Chart MUST generate a Kubernetes ConfigMap resource named `{{ include "tacito-agent.fullname" . }}-config`.
   - The ConfigMap MUST serialize all of the above parameters into flat environment variable key-value pairs following the `TS_AGENT_*` naming convention specified in `SPEC-FR-M5.1`, specifically:
     - `TS_AGENT_ID`
     - `TS_AGENT_NAME`
     - `TS_AGENT_TENANT_ID`
     - `TS_AGENT_COMMUNITY_ID`
     - `TS_AGENT_LLM_MODEL`
     - `TS_AGENT_LLM_ENDPOINT`
     - `TS_AGENT_LLM_TEMPERATURE`
     - `TS_AGENT_LLM_MAX_TOKENS`
     - `TS_AGENT_SYSTEM_PROMPT`
     - `TS_AGENT_REDIS_URL`
     - `TS_AGENT_REDIS_KEY_NAMESPACE`
     - `TS_AGENT_REDIS_TTL_SECONDS`
     - `TS_AGENT_QDRANT_URL`
     - `TS_AGENT_QDRANT_COLLECTION_NAME`
     - `TS_AGENT_QDRANT_VECTOR_DIMENSION`
     - `TS_AGENT_NATS_URL`
     - `TS_AGENT_S3_URL`
     - `TS_AGENT_S3_BUCKET`

4. **Deployment & Environment Variable Injection**:
   - The chart MUST deploy a standard Kubernetes `Deployment` resource running the agent image.
   - The deployment's Pod template MUST mount the ConfigMap keys as environment variables using the `envFrom` block targeting `{{ include "tacito-agent.fullname" . }}-config`.
   - The LLM credentials token/secret MUST be mounted securely using a separate Kubernetes Secret (either generated by the chart or referenced by name).

5. **Workload Probes & Constraints**:
   - The deployment MUST configure Liveness and Readiness probes pointing to the agent's `/healthz` and `/readyz` HTTP endpoints.
   - Standard resource requests/limits, nodeSelector, tolerations, and affinity configuration MUST be supported.

## Acceptance Criteria

1. **Helm Template Rendering**:
   - Running `helm template my-agent tools/helm/tacito-agent` renders a valid Deployment and ConfigMap resource with zero syntax or validation errors.
2. **Environment Variable Injection**:
   - The rendered ConfigMap contains all standard `TS_AGENT_*` keys, and the Deployment has an `envFrom` pointing to it.
3. **No External Chart Dependencies**:
   - The standalone chart contains zero dependencies in `Chart.yaml` on Keeper, Operator, or third-party infrastructure charts. It is completely isolated and decoupled.
4. **Health Probe Settings**:
   - Liveness (`/healthz`) and Readiness (`/readyz`) probes are defined with configurable timeouts.

## Test Plan

### Automated Tests
1. **Helm Template Testing**:
   - Create a test script `test/helm/test_agent_standalone_chart.sh` that runs `helm template` under different configurations and asserts the presence of the required Deployment, ConfigMap, and environment variables.
2. **Kubernetes Integration Testing**:
   - In integration/CI environments, dry-run template rendering against the target K8s cluster.

### Manual Verification
1. Render templates with custom credentials and prompt:
   ```bash
   helm template my-agent tools/helm/tacito-agent \
     --set agent.name="static-alpha" \
     --set agent.llm.model="gpt-4o" \
     --set nats.url="nats://nats:4222"
   ```
2. Verify all keys appear inside the generated ConfigMap block.
