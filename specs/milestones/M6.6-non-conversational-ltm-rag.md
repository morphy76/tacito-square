# Milestone M6.6: Non-Conversational Interactions & Long-Term Memory

| Field      | Value |
|------------|-------|
| Status     | ⬜ PLANNED |

## Goal

Consolidate non-conversational agent interaction patterns and reintroduce Long-Term Memory (LTM) with dual-nature semantics. Agents must be capable of operating in background, batch, or event-driven modes — without a persistent thread — while leveraging both ephemeral and persistent memory stores. RAG pipelines are introduced to ground agent responses in indexed knowledge bases.

## Context

M6.5 suspended LTM (Qdrant) and focused on conversational thread-based interactions. M6.6 reopens LTM with a refined model distinguishing two memory natures:

- **Persistent LTM**: Long-lived semantic memory stored in Qdrant. Survives agent restarts and community reassignments. Suitable for organizational knowledge, user preferences, domain expertise ingested over time. Scoped per tenant + agent (or community).
- **Ephemeral LTM**: Session-duration semantic memory. Lives longer than a single STM turn but is bounded by a configurable TTL or session lifecycle (e.g., a multi-step background job). Backed by Qdrant with aggressive TTL-based collection cleanup, or by Redis with embedding indexing. Does not pollute the persistent knowledge base.

Non-conversational interactions include:
- **Fire-and-forget tasks**: a single NATS message triggers an agent action; no response thread is expected.
- **Background jobs**: multi-step agent processing without a human-in-the-loop; results written to S3 or emitted on NATS.
- **Ingestion pipelines**: structured documents fed to agents for embedding, summarization, or indexing into persistent LTM.
- **Scheduled triggers**: periodic agent activation driven by cron-like events.

## Deliverable

An agent receives a non-conversational trigger event (e.g., ingest document, run background report). It uses ephemeral LTM to accumulate intermediate context across steps. Upon completion, results are persisted in persistent LTM and/or written to S3. A second agent query later uses RAG to retrieve and ground its response from the indexed knowledge.

## Key Design Decisions to Resolve at Spec Time

- **Ephemeral LTM backing**: Qdrant with TTL-scoped collections vs. Redis with vector indexing (e.g., Redis Stack). Trade-off: Qdrant reuse simplifies the adapter but adds collection management overhead; Redis Stack is lighter but adds a dependency.
- **LTM scope boundary**: Is persistent LTM scoped per agent (one collection per agent), per community, or per tenant? Must account for shared organizational knowledge use cases.
- **Ingestion trigger**: Does ingestion always flow through an agent (cognitive), or is there a direct Keeper-managed ingestion API that bypasses the agent loop?
- **RAG in hub vs. spoke**: Should RAG retrieval happen at the hub level (shared retrieval for all spokes) or at the spoke level (each spoke retrieves from its own LTM)?
- **Supersession of M8**: This milestone partially supersedes M8 (RAG & LTM) — SPEC-FR-M8.1 (Design architectural integration patterns) should be reviewed for compatibility or marked superseded.
